# 麦麦：对话逻辑、动作与回复效果

2026-10-25。本轮以用户已确认的悬浮人物与贴身对话为基础：预算配餐、菜单与单点、门店、优惠都在聊天中完成；卡片是对话的一部分，用户可以点卡片，也可以继续用文字改。语气正常友好，偶尔玩海鸥薯条梗。

## 一轮交流怎样发生

点麦麦 → 挥手 → 侧耳听。输入时保持倾听；发送后根据任务切换动作。处理结束发简短文字，再展示结果卡片。麦麦用口型和手势回应约 1.5 秒，随后回到倾听；缺条件时改为期待等待。消息逐条出现，不逐字模拟所谓“推理过程”，状态只解释正在做的任务。

动画是任务状态的表达，不能作为查询成功或已经下单的证据。真正的完成依据是带请求标识、来源与时间的业务结果。当前页面使用演示脚本与历史整单报价，MCP 商品图片已经实际查询并替换，但聊天还没有实时模型与工具服务。

| 用户说 / 事件 | 麦麦动作 | 回复产出 | 下一步 |
| --- | --- | --- | --- |
| 点击人物、开始输入 | 挥手一次 → 侧耳听 `waving → listen` | 展开贴身对话，保留当前页面历史 | 等用户发送 |
| “你好”“谢谢” | 倾听 → 开口回应 `listen → talk` | 一两句友好回应，不假装查菜单 | 回到倾听，保留餐单 |
| “30 元配一餐”，还没选店 | 想一想 → 回应 → 期待等待 `review → talk → waiting` | 追问城市 / 地标与必要条件，不直接报价 | 用户确认具体取餐门店 |
| “北京站附近” | 想一想 → 翻册子 → 回应 `review → search → talk` | 门店名称、地址、编码、营业 / 预约信息与选择卡；原型仅有明确标注的测试店 | 用户确认，不自动选最近店 |
| 门店已定，按预算挑餐 | 想一想 → 翻册子 → 回应 | 最多三份完整餐单卡：圆形商品原图、组成与数量、整单价、预算余量、报价时间 | 选择、看组成或调整条件 |
| “看看单点”“第二份有什么” | 想一想 → 翻册子 → 回应 | 圆图单品或套餐组成；没核对的独立售价不显示 | 继续询问 / 选择 |
| “选第二份” | 想一想 → 回应 | 餐单草稿，明确尚未下单；保留门店与预算 | 可继续修改，不反复庆祝 |
| “饮料换大杯” | 想一想 → 计算器 → 回应 `review → calculate → talk` | 先显示修改和“旧报价失效”，再展示完整重新核价结果 | 核价失败保留待核价草稿 |
| 本次整单核价确已成功 | 开口回应 → 海鸥偷薯条一次 `talk → celebrate` | 明确报价来源和时间，金额由工具结果决定 | 回到倾听，不扣餐单薯条 |
| “看看确认单” | 想一想 → 回应 | 门店、取餐方式、所有实际选择、数量、价格、优惠与核价时间；标明尚未下单 | 待用户在官方渠道完成 |
| “我有什么优惠券” | 想一想 → 翻册子 → 回应 | 正式版显示券归属、有效期、门店 / 商品限制；当前演示明确未实时查询 | 不自动领券、不声称拥有券 |
| 条件不够 / “就这个”指向不明 | 回应 → 期待等待 | 合并追问必要条件，说明哪个信息影响结果 | 不猜测偏好或确认对象 |
| 业务失败 / 超时 | 困难动作 `failed` → 回到当前状态 | 一句具体原因 + 重试或修改条件；保留草稿 | 取消排队庆祝 |
| 用户按“停止” | 立即结束处理动作，回到倾听 / 期待等待 | 显示已停止，已修改餐单继续标为待核价 | 重试不会复用失效旧价 |
| “摸摸你”“休息一下”“吃根薯条” | 摸头 / 打盹 / 吃薯条 | 简短陪伴反馈 | 不改门店、数量、金额或报价 |
| 收起对话 | 继续当前任务；无任务才安静待机 | 新回复用人物旁提示保留 | 重开看同一段聊天 |

## 三段具体回复

预算配餐：

> 你：30 元，一个人，要汉堡和无糖饮料。
>
> 麦麦：在哪家店取餐？告诉我城市或地标，我再帮你挑。
>
> 你确认门店后：整餐 30 元以内，历史记录里有 3 份可比较。含汉堡、中薯和中杯无糖可乐；以下为历史报价。
>
> 随后显示餐单卡；麦麦：可以说“选第二份”，也可以先看组成。

继续修改：

> 你：第二份换大杯无糖可乐。
>
> 麦麦：饮料已改为大杯无糖可乐。旧总价已失效，我再核对修改后的整份餐单。
>
> 计算器动作结束后：已读取对应选择的历史整单核价。当前价格仍需实时查询。
>
> 卡片显示：¥28.50，预算余 ¥1.50；完整组成与历史核价时间；尚未下单。之后海鸥偷一根薯条庆祝一次。

没有结果：

> 你：两个人，30 元，不要薯条。
>
> 麦麦：当前只收录单人餐历史样例，无法验证这份要求。人数和预算已保留，需要实时菜单才能重新搭配。
>
> 不出现“帮你配好了”、假价格或成功庆祝；用户可以改条件或继续聊。

上述文案是产品交互设计；原型只支持已记录的有限路径，不等于已经具备任意语义理解。自由偏好、多人配餐、换店和账户优惠仍需后端实现。

## 回复卡片与图片

每条回复先回答问题，再展示相关卡片；金额、限制和错误不用玩梗。套餐卡展示最多三个候选，单品只展示名称与有据可查的属性；用户选择后，草稿卡展开完整组成。修改后此前草稿标成历史记录并禁用旧操作，最新餐单始终为准。

商品图采用 MCP `query-meal-detail` 原样返回的 HTTPS 地址，按商品编码关联。圆形容器使用 `object-fit: contain`，不改照片颜色、不像素化、不裁切餐品。套餐原图是标准搭配展示；换了饮料后，卡片的文字与逐项图片才是实际选择，不能把套餐照片当作定制后的合成图。中杯 3071 与大杯 3111 使用各自原图。

本轮查询地点仍沿用开发测试门店 1950072（麦当劳北京崇外新世界餐厅），不表示用户位置。2026-10-25 14:05–14:06（UTC+8）实际取得 7 个商品的原图：2 个套餐、吉士汉堡包、麦香鸡、中薯条、中杯 / 大杯无糖可乐。7 个图片地址均通过 HTTP 200、image/png 检查。只保存编码、名称、地址与时间；不保存账户原始响应或凭证，也不下载照片绕过展示限制。

旧记录中的龙焰套餐 9900016073 与龙焰鸡腿堡 521952 当前返回“未匹配到商品”。背景陈列仅显示有原图的两份套餐；历史聊天卡保留并标明当前查不到，图片位置显示“暂无原图”，不借用其他汉堡图片。网络加载失败显示“图片未加载”，名称、金额和聊天仍可用。

图片来源与报价来源分别记录：本轮取得图片不代表重新核价；已有整单金额仍来自 2026-10-24 的历史核价。图片可在当前演示展示不等于获得任意商业使用授权。可检查 [商品图片来源快照](product-images.snapshot.json)。

## 状态、优先级与未来接入

正在处理的任务优先于陪伴动作；停止、失败、新请求会清除旧队列。成功反馈以请求标识去重，只在本次核价完成时触发；浏览卡片、选择或打开确认单不反复触发。减少动态使用静态关键帧，文字状态与操作保留。当前页刷新清空聊天，不上传聊天、不在前端放 Token。

正式服务端应返回：`requestId`、`status`（澄清 / 查询 / 核价 / 回复 / 失败 / 停止）、简短文字、卡片、门店与餐单版本、报价来源与时间、可恢复错误。前端按业务事件播放动作；用户修改内容先使旧报价失效，成功才接受新价。模型不直接决定价格，不因自然语言“就这个”创建订单。正式模型、会话持久化和服务端鉴权为后续工程事项，当前设计没有代替这些能力。
